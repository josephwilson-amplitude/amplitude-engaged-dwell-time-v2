Product Analytics

Why Dwell Time Is Lying to You

In media, e-commerce and SaaS product analytics, time on page is one of the most cited engagement signals. But it has a fundamental flaw.

Raw dwell time is a timestamp delta. It measures the gap between when a page loaded and when the browser navigated away. It does not measure whether any human attention was directed at the page during that window.

"A three-minute session and a thirty-second session look identical if the user walked away at the right moment."

The result is a metric that systematically overstates engagement. Teams celebrate rising average session durations that are, in part, just rising rates of distraction, multi-tasking, and forgotten open tabs.

The fix is not complicated. The browser exposes a rich set of passive signals that prove a human is present and attending: mouse movements, scroll events, keyboard activity, clicks. Combine those with an inactivity window and you have a much cleaner picture of actual attention.

Plugin Architecture

How the Plugin Works

A single enrichment plugin. No extra Amplitude events for most sessions.

The plugin uses Amplitude's built-in page counter to determine its behaviour. On the first page in a session, it starts tracking engaged time using a sliding activity window. When the user navigates to any subsequent page, the previous page's dwell data is attached directly to the incoming page view event.

The page counter gate

When a new [Amplitude] Page Viewed event passes through execute(), the plugin reads [Amplitude] Page Counter. If it is 1, this is the first page — tracking begins and no data is attached yet. If it is 2 or higher, the previous page's data is snapshotted and attached as et_* properties before the event reaches Amplitude's servers.

This means dwell time data travels on events that were already going to fire. No additional event volume for multi-page sessions.

Single-page sessions

When a user lands and closes the browser without ever navigating, the page counter never exceeds 1. In that case the plugin falls back to a dedicated [Engaged Dwell] Page Exit event, fired on visibilitychange, pagehide, or beforeunload. This event carries the same five et_* properties as any piggybacked page view, so both event types slot into the same Amplitude metric without any special handling.

Data Model

The Property Schema

Five properties, same names on both event types, so they join cleanly in Amplitude.

Whether dwell data arrives on a [Engaged Dwell] Page Exit event (single-page sessions) or as piggybacked properties on [Amplitude] Page Viewed (multi-page sessions), the property names are identical. This means you can build a single metric — et_engaged_time_ms, grouped by et_page_title — and drop both event types in without any property mapping.

What is not captured

The last page of any multi-page session does not have a subsequent page view to carry its data. This is an intentional tradeoff: capturing it would require a dedicated exit event on every session, which is the cost problem the architecture is designed to avoid. For most analytical questions — average engaged time by page, content quality scoring, funnel drop-off — the gap is acceptable.

Single-page sessions are fully covered When a user lands and leaves without navigating, the page counter never exceeds 1 and a [Engaged Dwell] Page Exit event fires on browser close or tab hide.

How the Plugin Works

Architecture, event schema, SPA integration, and risks.

Architecture

The plugin uses Amplitude's [Amplitude] Page Counter — already present on every [Amplitude] Page Viewed event — to determine which of two paths to take per session.

Page Exit
Single-page sessions — page counter stays at 1 Fired on browser close, tab hide, or navigation away. Uses visibilitychange, pagehide, and beforeunload — deduplicated with a hasFired flag. Carries the full et_* schema for the only page visited.
Piggyback
Multi-page sessions — page counter ≥ 2 When each new [Amplitude] Page Viewed event passes through execute(), the previous page's dwell data is snapshotted and attached as et_* properties. No extra events created. Last-page dwell time is intentionally not captured.

Event flow in a 3-page session

1
User lands on /page-1 [Amplitude] Page Viewed fires (counter = 1). Plugin starts the tick accumulator and stores page URL and title. No et_* data attached yet.
2
User navigates to /page-2 [Amplitude] Page Viewed fires (counter = 2). Plugin's execute() snapshots /page-1 dwell data, attaches it as et_* properties on this event, then resets the accumulator for /page-2.
3
User navigates to /page-3 [Amplitude] Page Viewed fires (counter = 3). Same as step 2 — /page-2 data attached to this event.
4
User closes browser on /page-3 Exit signals fire. Page counter is 3 — the plugin does nothing. /page-3 dwell time is not captured (accepted gap).

Property schema

All five properties use the et_ prefix and appear with identical names on both event types. This lets you build a single Amplitude metric — et_engaged_time_ms grouped by et_page_title — using both [Engaged Dwell] Page Exit and [Amplitude] Page Viewed as the event filter.

PropertyDescription
et_engaged_time_msMilliseconds the user was actively engaged. Stops accumulating after inactivityThreshold ms of no input.
et_total_time_msRaw dwell time from page entry to navigation or exit.
et_page_urlFull URL of the page being measured (not the current page for piggybacked events).
et_page_titleDocument title of the page being measured.
et_inactivity_threshold_msThe inactivity window used (default 30,000 ms). Useful for filtering if you run different thresholds across experiments.

SPA integration

No router hook is required. The plugin detects navigation automatically: when a new [Amplitude] Page Viewed event passes through execute() with a counter of 2 or higher, the plugin knows a navigation just happened and handles the snapshot and reset internally.

The only prerequisite is that Amplitude's page view tracking fires on each SPA route change. This is standard configuration:

// Option A — automatic (Amplitude Browser SDK 2)
amplitude.init('YOUR_API_KEY', {
  defaultTracking: {
    pageViews: true,   // fires on history pushState / replaceState
  }
});

// Option B — manual (call in your router hook)
router.afterEach((to) => {
  amplitude.track('[Amplitude] Page Viewed', {
    '[Amplitude] Page URL':   to.fullPath,
    '[Amplitude] Page Title': document.title,
  });
});

The plugin reads [Amplitude] Page Counter from the event properties. If this value has not yet been set by Amplitude's own enrichment pipeline when your plugin runs, the plugin falls back to a self-tracked counter that increments on each [Amplitude] Page Viewed it sees.

Installation

// 1. Add the plugin file to your project, then:
import * as amplitude from '@amplitude/analytics-browser';

const plugin = createEngagedDwellTimePlugin({
  inactivityThreshold: 30_000,  // ms before user is considered idle
});

amplitude.init('YOUR_API_KEY', {
  defaultTracking: { pageViews: true }
});

amplitude.add(plugin);

Risks and tradeoffs

Low — Hard browser crash

No JavaScript solution can recover data when the browser process is killed. Affects ~1–2% of sessions across all analytics tools equally.

Low — Last-page data gap

The final page in any multi-page session is not captured. Intentional tradeoff to avoid extra event volume. Does not affect pages 1 through N-1.

Low — iOS Safari

beforeunload is unreliable on iOS. Covered by visibilitychange, which fires reliably when the user switches apps or locks the screen.

Medium — Page counter availability

If this plugin runs before Amplitude's page tracking plugin in the enrichment pipeline, [Amplitude] Page Counter may not be set. The self-tracked fallback counter handles this, but ordering plugins explicitly is recommended.

Event volume impact

For a typical multi-page session (3+ pages), the plugin adds zero extra events. Dwell data travels on [Amplitude] Page Viewed events already being sent.

The only new event is [Engaged Dwell] Page Exit, which fires exclusively for single-page sessions — users who land and leave without navigating. If your bounce rate is 40%, approximately 40% of sessions will generate one extra event. Sessions with two or more page views generate none.
